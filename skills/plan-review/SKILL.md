# 深度审核实施计划

审核计划能否交付用户约定范围内的完整产品，并让零上下文的新 Agent 能够直接按步骤执行。审核者必须**先主动判断本次改造需要什么模块划分、设计模式、抽象封装与 SDK 复用方案，再核对计划是否成立**，不能停留在检查计划有没有写模式名称或复述计划内容。

默认在主会话只读审核；仅在用户明确授权修改计划时才直接更新计划文件。审核结论“允许执行”代表技术方案与阶段条件就绪，不代替或撤销用户的实施授权。

## 1. 核对目标、代码证据与复审状态

- **锁定审核对象与原始需求**：读取用户指定的计划文件或粘贴内容（无计划时先索取，不凭空编造后再审核）。对照用户原始需求、已确认决定和明确不做项（不将已排除的可选扩展重新加回），提取最终可消费效果与必需能力。
- **建立真实证据**：按需读取相关源码、目录结构、调用方、测试、脚本与依赖配置，核实既有模块与可复用能力。涉及具体 SDK/API、许可证或版本兼容时，优先通过官方文档工具及项目锁文件查证；无法查证的标为**待验证**，绝不编造 API、版本号或跑分。若仅提供计划文本，则针对文本审核并注明未核对仓库环境。
- **处理复审、关闭与重开**：复审时沿用原问题编号（如 `R1`、`R2`）核对关闭条件。已补入所需契约、阶段或检测安排的计划问题即予关闭并移出未决表（在顶部结论一句话说明已关闭编号）；已关闭的历史问题（如 `R7`）无新反证或范围变化不得重开；沿用已成立的设计决定，不因个人偏好重新换模式。

## 2. 逐项诊断五大核心维度

按任务实际场景深入审查（纯静态或局部简单修改不强加分布式、复杂类层级或多余缓存，但需写明现有简单结构已足够的证据）：

### A. 模块划分、设计模式与抽象封装

1. **模块化目录结构（防散装堆文件）**：检查计划是否按领域职责（如编排入口、具体格式/策略实现、底层适配/IO、测试）规划了清晰的目录结构树；拦截将多个不同职责的新文件散装堆在同一目录的做法。
2. **主动诊断复杂度与模式选型**：
   - 从真实问题出发比较候选方案（至少对比现有/更简单做法）：多种算法或格式变体比较**策略模式**；严格先后顺序、分支与回滚比较**显式工作流/流水线或直接函数组合**（拦截用无顺序保证的观察者/事件回调承载主流程）；受状态严格约束的操作比较**显式状态机/状态中心**；隔离外部 SDK 差异比较**窄适配器**。
   - 计划未选型时，由审核者直接给出具体选型建议；计划选错或过度设计（如为单一实现预建 `AbstractFactory`/注册中心）时，指出替换方案与理由。
3. **核对五项封装证据（拦截假封装）**：
   - **职责与所有权**：业务顺序、共同规则、状态迁移和资源（快照、临时文件）是否有唯一权威所有者？
   - **对外契约**：入口签名、输入输出、失败/取消/提交竞争语义是否明确（提案接口须标注，不冒充现有 API）？
   - **共性与变化点**：集中什么共性、隔离什么变化，取舍理由是否成立？
   - **目标调用路径与旧职责退出**：`入口 → 规则/编排所有者 → 策略/SDK → 结果消费` 链路是否闭环？原本散落在 UI 或旧分支中的重复校验、状态同步和清理何时退出？
   - **代码落点与结构验收**：是否用本次一个真实变化场景（如修改重试规则或新增格式）证明只需改唯一入口，无需多处同步修改？
   - **另需严厉拦截假封装**：新增 `Service/Manager/Runner` 仅做透传转发、套上策略接口后各实现仍各自控制全流程或清理、新旧两套状态/控制中心并存，均判为 **P1** 结构缺陷。

### B. SDK 与现成能力复用

- 按 **“仓库已有模块 → 标准库/平台内建 → 已安装依赖 → 官方或成熟第三方 SDK → 必要自建”** 核对。
- 检查是否重复造轮子（如已有原子写入、任务管理或成熟解析库却自行手写），或一边引入 SDK 一边又重复手写其已覆盖的底层逻辑。
- 检查候选 SDK 的版本、API、运行环境、许可证与包体约束是否已核实；把未验证的候选 SDK 当成已确认事实直接用于后续编码阶段的，必须拦截并要求补齐查证门槛或替换。

### C. 目标一致性、完整交付与新 Agent 可执行性

- **端到端真交付**：走通“进入 → 输入 → 处理 → 真实可消费结果（如文件可打开、数据可重读、状态可查询）”及失败恢复路径。拦截用成功提示（Toast）、日志打印或占位空壳代替真实交付，或把本次必需能力推给“后续完善”。
- **新 Agent 零上下文可执行**：检查每个阶段是否明确了前置条件、具体文件与符号、调用方迁移步骤、源自项目真实配置的验证命令及可观察完成判据。

### D. 性能、按需加载与 CPU 执行位置检测

- **规模、复杂度与真实数据**：核查典型与极端输入规模（如大文件、高并发）、内存峰值、全量加载或阻塞主线程机制；拦截无测量依据的编造耗时（如“0ms”“50ms”）。
- **按需加载与静态导入链**：区分启动/首屏必需能力与低频重模块（如 PDF/TIFF 库）。检查动态 `import()` 是否被入口、工具栏引用、`index` barrel/re-export、共享依赖或顶层初始化副作用破坏而仍留在首屏关键路径。
- **异步 I/O 与 CPU 计算位置**：严格区分 `async/await`（不自动移出主线程）与同步重 CPU 计算（需评估 Worker 或分块，并明确请求去重、关闭后过期结果丢弃、底层取消与 Worker/内存释放所有者）。
- **性能检测闭环**：检查计划是否在验证阶段安排了构建分包产物检查、首次加载轨迹检查及大输入下的响应/内存释放检测。

### E. 安全边界、数据保护、高可用韧性与负向检测

- **不可信输入与信任边界**：顺着外部输入（文件路径、压缩包条目、外部配置、网络数据）到文件写入、命令执行、渲染或外部服务的链路，检查路径规范化与防目录穿越/符号链接逃逸、解压大小/条目数/压缩比/并发限额及凭证保护。
- **原子提交、失败恢复与高可用韧性**：涉及覆盖写入或状态迁移时，检查是否先在临时区完成处理与校验、再原子提交落盘；严禁在未确认新结果成功前先删除或覆盖旧数据（P0 数据丢失风险）。检查中途取消或提交竞争时的旧数据保留与临时资源清理；涉及外部调用或并发状态时，核查超时与幂等边界、非核心故障隔离降级、错误传播所有权（拦截吞掉异常返回假成功或在无恢复能力的中间层逐层乱套 `try-catch`）。
- **安全与负向检测闭环**：检查计划是否明确安排了恶意路径、损坏输入、超限数据、写入失败及取消竞争等负向检测用例。

## 3. 分级判定与查证门槛区分

先找反证排除误报，合并同根因问题，按证据状态（**已确认缺口 / 推断 / 待验证**）和严重度分级：

- **P0（立即阻断）**：将导致数据丢失（如提交前先删旧项目）、路径穿越任意写、敏感凭证泄露等严重后果。
- **P1（阻塞实施）**：核心需求未兑现、缺少必要封装或假封装保留冲突控制源、模式选型错误破坏业务约束、重模块假延迟加载或主线程重计算卡死、缺少关键安全边界或把未核实 SDK 当作既定事实。
- **P2（非阻塞缺陷）**：不阻断核心交付，但影响维护边界、次要体验或测试充分性；需明确修改要求与关闭条件，不冻结无关阶段。
- **待查证（阶段门槛）**：当某项未知（如候选 SDK 细节、Worker 终止释放表现）已在计划中设置了独立的 `S0` 最小探针、明确完成判据、失败后的停止或备选方案，且阻塞了依赖它的 `S1` 时，它是**已妥善管理的查证门槛**——此时**计划质量可通过**，结论写“允许执行 S0；S1 等待 S0 查证通过后执行”，不把已妥善设置的门槛同时判为 P0/P1 设计缺陷。反之，若没有独立判据和失败备选、只写“实施时再看”，则判为 P1 计划缺陷。
- **可选改进**：非必需的优化建议，绝不伪装成阻塞项。

## 4. 按结构化模板输出审核反馈

读取并严格按照 [审核结果模板](assets/review-template.md) 输出（使用中文），让用户一眼看清三个核心问题，并可直接作为后续修订或按计划实施的交接依据：

1. **顶部《计划审核结论》**：第一行直接给出**是否允许执行**（`允许执行` / `允许执行 S0；S1 等待查证` / `暂不允许执行 S1：阻塞于 R1、R2` / `待判定：缺少关键材料`），紧接着用两行说明**计划质量与阶段就绪状态（含复审已关闭/保持关闭的编号）**以及**核心架构、模块目录与 SDK 复用判断**。
2. **《1. 风险与待查证清单（哪些地方涉及风险）》**：列出所有未关闭的 `P0 / P1 / P2 / 待查证` 项，写清风险维度、具体位置与证据状态、触发条件与后果链路、受影响阶段。
3. **《2. 计划必改项与修订清单（需要改动哪些地方）》**：与上方编号一一对应（可附带 `可选改进`），明确需要改动哪个章节或模块路径、当前方案与候选模式/SDK 的比较取舍、**具体怎么改（职责所有权、函数签名/契约、目标调用链、旧职责退出、性能与安全检测补充）**，以及本轮计划问题的关闭条件与实施后的验收方式。

若审核发现计划完全闭环、无未决风险或必改项，在两张表下写“无”，并在顶部结论中简要列出支撑通过的关键架构、复用与验证证据。
