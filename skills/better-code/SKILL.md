# 承接设计并落实高内聚代码

让功能的业务规则、执行顺序、状态迁移和资源生命周期各有**唯一权威归属**，并落实到真实的模块化代码中。杜绝散装堆放文件、透传外壳（假封装）和新旧多套控制中心并存的胶水代码。

只讨论方案或走查候选实现时不修改文件、不宣称已运行测试；用户已授权实施且无阻塞项时直接落地并验证。

## 0. 解析可选参数 `worktree`（代码隔离执行模式）

检查技能调用参数（`$ARGUMENTS`）或用户请求中是否指定了 `worktree`（例如 `/better-code worktree ...`、`--worktree` 或明确要求“用 worktree 方式编写代码”）：

- **未指定 `worktree`（默认）**：直接在当前工作目录执行后续步骤，严禁擅自创建分支或切换 worktree。
- **指定了 `worktree`**：在动手修改任何代码前，先建立独立的 Git worktree 隔离环境，确保原主工作目录零污染：
  1. **进入或创建隔离 worktree**：若宿主环境提供 `EnterWorktree` 工具，优先调用该工具创建并切入以本次任务命名的 worktree；若在纯命令行环境下，先检查 `git worktree list`，在仓库外同级或 `.worktrees/<task-slug>` 下通过 `git worktree add -b feat/<task-slug> <worktree-path>` 创建独立工作树并切换进入。
  2. **全程在 worktree 内完成闭环**：所有源码编辑、依赖复用核对、测试验证与结构验收均在该 worktree 目录内执行，绝不改动原工作区文件。
  3. **交付时汇报 worktree 信息**：在最终交付证据中明确列出 worktree 绝对路径、所在分支及变更状态，方便用户直接在主工作区对比、合并或清理。

## 1. 核对设计依据、授权边界与锁文件事实

- **区分决定状态**：从用户请求、当前计划与审核结论中区分**已确认决定**、**未采纳的审核建议**（如审核提议但用户未确认的抽象工厂或插件框架，不得擅自当成既定方案）与**待验证假设**。没有计划或审核报告时，直接基于需求与源码独立工作，不强制要求先做一轮计划审核。
- **核对真实代码与依赖锁文件**：查看实际源码、调用方、依赖清单与锁文件版本（如 `package-lock.json` / `pnpm-lock.yaml`），核对所需 API 的真实导出与语义（输入输出、错误、底层取消 `signal`、资源释放）。
- **处理分支、小改动高可用通道与复杂度升级**：
  - **已确认方案与代码/锁版本匹配** → 直接沿用既有模式、职责与 SDK 决定，不重做整套模式竞选。
  - **职责清晰的局部小改动（免除形式主义，保留高可用底线）**（如共享校验函数 `canSubmit` 补 `value.trim().length > 0`） → 一句话确认现有函数已拥有唯一权威规则，省去目录树、模式竞选和交接大表；但**依然严格执行第 3 节的高可用编码标准**（强类型边界、不乱套 `try-catch` 或吞异常、不复制第二份规则、补齐正负向与边界测试）。
  - **小改动探查后发现复杂面扩大 → 停止边想边改，自动升级至计划流程**
    用户按局部修改发起请求，但阅读源码后出现以下任一信号时触发：
    1. 需跨多个领域重构散落的控制中心，或重划模块目录；
    2. 需引入新 SDK，或存在未验证的运行时 / 并发 / 取消机制（需 `S0` 探针）；
    3. 触及数据原子覆盖或迁移、安全信任边界、首屏关键路径改造。

    触发后先产出完整可执行计划，把复杂面摆在明面确认再实施。
    例外：仅为中等明确需求，且用户要求直接按设计给出方案并落地时，在第 2 节内完成适度设计即可，不机械卡死。
  - **发现原方案假设不成立的新事实**（例如计划依赖某 SDK `2.0` 的 `signal` 取消并释放句柄，但锁文件实际为 `1.3` 且无取消/停止 API） → **严禁把外层忽略回调冒充底层已停止，严禁偷偷升级依赖或从零自建插件框架**。保留其余仍有效的架构决定，仅重新判断失效部分，明确记录 `原决定 → 新证据 → 受影响契约或阶段 → 候选修订与验收`；受阻阶段暂停并交用户决定（升级依赖或调整取消承诺），不依赖该假设的已授权本地工作继续推进。

## 2. 按需完成模块化目录与模式选型（仅针对缺失或失效部分）

当没有现成计划或原设计失效时，从真实复杂度出发完成适度设计（已有有效计划时跳过本步直接引用）：

1. **模块化目录划分**：按领域职责划分子目录（如编排用例、具体策略/格式实现、底层适配/IO、测试），共变的规则放近、独立变化的能力隔开，不在同一目录散装堆放 `helper/util`。
2. **模式选型与简单方案对比**：每次选型必须与现有或更简单的函数组合对比，说明解决什么问题、谁拥有职责、隐藏什么复杂度：
   - **多种算法/格式实现** → **策略模式**（函数或对象均可；策略只负责单一转换/编码，不接管查询、存储或整个用例流程）。
   - **多步骤严格顺序、分支与清理** → **显式用例/工作流或直接函数组合**（不用观察者/事件回调顺序承载主流程）。
   - **合法操作受状态严格约束** → **显式状态机/状态中心**（单一权威状态迁移入口）。
   - **隔离外部协议/SDK 差异** → **窄适配器**（保留真实错误与取消语义，不吞业务规则）。
   - **单一稳定实现** → 直接用清晰的函数与模块，不为未来可能扩展预建工厂、注册中心或插件生态，不引入用户明确排除的能力（如自动重试、断点恢复）。

## 3. 落实高内聚封装、SDK 边界与加载/CPU 调度

写代码或审查候选实现时，逐项落实以下硬性标准：

- **拒绝透传外壳与多控制中心**：核心用例/编排模块必须真正拥有“查询/输入 → 处理/编码 → 存储/输出 → 失败与取消清理”的顺序和终态。若新增 `Service/Manager/Runner` 只是转发调用，而旧函数、控制器回调和 UI 仍各自决定顺序、终态与清理，属于**假封装**，哪怕行为测试全绿也必须判**结构验收不通过**。
- **用强类型约束与错误所有权消灭防御性 `try-catch`**：
  - **在入口把“未校验原始输入”收敛为“已验证领域类型”**（Parse, don't validate）：在系统边界（入参解析、配置/反序列化、外部响应）一次性完成校验与类型收窄；内部函数直接接收已保证合法的强类型（如非空结构、有限字面量联合、受控状态类型），不再在内部写防御性的空值猜测或 `try-catch`。
  - **用可辨识联合（Discriminated Union / Result）表达预期业务分支**：对“校验未通过、资源不存在、提交后取消 `tooLate`”等**预期内的业务结果**，优先用显式返回类型（如 `{ ok: true, data } | { ok: false, reason: 'tooLate' | 'invalid' }`）建模并由编译器强制调用方处理分支，而不是靠抛异常再 `try-catch` 当控制流。
  - **禁止 `any` 与吞异常的宽泛返回类型**：严禁用 `any`、无约束 `Record<string, unknown>` 或把返回类型放宽为 `T | null` 来配合 `catch { return null }` 掩盖异常。
  - **仅在 4 类真正能处理的边界写 `try-catch`**：① 本地资源清理/回滚（`try...finally` 或清理后立即重抛）；② 跨模块边界补充业务上下文（保留原始 `cause`、阶段与目标 ID）；③ 有界幂等重试或非核心功能降级；④ 最外层统一错误入口。无恢复能力的内部步骤直接让异常按契约上抛。
- **落实 SDK 与现有能力复用**：实际调用已核实的仓库能力（如现有队列、流查询、编码器、对象存储、功能内加载器）与匹配版本的 SDK，本地代码只保留领域规则与薄适配，不重复手写 SDK 已覆盖的协议、解析或生命周期。
- **按需加载与 CPU 执行位置**：
  - **保留必需与轻量能力提前就绪**：启动必需配置与轻量常量保留同步/提前加载，不机械将所有模块异步化。
  - **确保重模块真正退出首屏路径**：低频面板、重编码器/SDK 或大字体按需加载时，必须切断直接/间接静态导入、`index` barrel/re-export 及顶层初始化副作用；不能只在外层包一个动态 `import()` 而入口仍从公共 barrel 静态拉入全部模块。
  - **区分异步等待与 CPU 线程调度**：`async/await`、Promise 或动态导入不会把同步重计算（如像素循环解码、大文件压缩）移出主线程；根据规模评估 Worker 或分块让出执行权，并计入传输与销毁成本。
  - **收拢加载状态与竞态控制**：优先复用现有功能内加载器集中管理就绪状态，实现同目标并发请求去重（避免每次点击重复创建 Promise）、缓存隔离、失败后可重试恢复（不永久保留同一个 rejected Promise），以及面板关闭/切换后丢弃过期结果并释放资源；区分外层停止等待与底层真实取消（底层取消能力未知时先列为待核实）。

## 4. 迁移控制权并执行“行为 + 结构”双验收

1. **接通真实路径并拔除旧控制中心**：迁移调用方、类型、导出与测试，确保入口真正走新路径，并移除旧分支、控制器或 UI 中散落的重复校验、状态修补和清理逻辑（避免新旧双轨永久并存）。
2. **行为与加载轨迹验收**：在授权内运行项目真实配置的最小检查（覆盖正常、边界、失败、取消竞态与清理）；涉及按需加载时，要求核对生产构建产物、实际请求/初始化轨迹及首次使用/失败恢复/关闭重入表现，不凭源码写了 `import()` 或 mock 通过就宣称首屏优化完成，不编造耗时或包体数字。
3. **结构验收（同类变化检验）与终检衔接**：用本次一个真实变化场景（如“新增一种导出格式”或“修改统一校验/重试规则”）核验修改入口，确认只需修改唯一权威入口及对应契约测试，无需在多处重复同步业务知识。实际编码完成后，按代码审查的核心标准对变更做最终审查（正确性、并发、封装、加载与安全四维）。
