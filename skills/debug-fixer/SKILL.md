# 实证驱动的自动化调试与根因修复

本技能以**实质性运行时证据**取代“盲猜打补丁”，扫描 → 判断 → 埋点 → 自动复现取证 → 分析日志 → 修复或转重构 → 清理验证一次跑完。其中只读扫描、注入/清理自己打的埋点、写入和删除 `.debug/logs/` 下的日志均无需逐步征求确认；涉及业务代码的实际修改、大范围架构调整、删除既有文件或影响共享行为的操作，仍按项目规则先向用户说明并取得同意。

## 核心铁律

1. **只允许一次高把握静态直修**：静态推理最多只允许在单点确定性根因上尝试 1 次。若涉及异步竞态、缓存时序、多端状态、CSS×JS 叠加，或第 1 次直修未通过验证，**严禁猜第 2 次**，立即回滚无效修改并注入埋点采集运行时证据。
2. **禁止裸写 `console.log / print`**：所有埋点必须使用带 `// #region DEBUG [sessionId: <id>]` 标记的标准静默模板，统一以 JSON Lines 格式落盘到 `.debug/logs/<session_id>.log`，确保可按会话聚合分析、且可通过脚本一键零残留清除。
3. **内置“简单 Bug vs 整体重构”判断层**：调试不是无底洞地贴膏药。一旦在扫描或日志分析中发现问题属于结构性缺陷（状态分裂、多入口失控、缺乏统一契约、牵一发而动全身），**立即停止单点打补丁**，清理埋点后转入重构计划的制定。
4. **全自动闭环验证与清理**：优先通过项目测试、CLI 脚本、HTTP 请求或 `ego-browser` 自动触发复现并读取日志；验证通过后自动运行清理脚本，不在代码库或工作区留下任何调试痕迹。

---

## Step 1：主上下文四维扫描与第一次“重构判断门禁”

在主上下文中直接利用 `Grep` / `Read` 从四个维度交叉扫描故障链路，并对比项目中同类的正常代码：

1. **数据流（Data Flow）**：数据从源头（API/Store/Props/文件/参数）→ 转换节点（normalize/map/转换）→ 消费端的完整生命周期，以及所有并发写入点。
2. **控制流（Control Flow）**：实际执行顺序、异步/事件/回调导致的乱序窗口（后发先至覆盖）、条件分支、副作用传播链。
3. **视觉与布局（Visual，前端适用）**：DOM 实际几何尺寸（`getBoundingClientRect`）× CSS 计算样式（flex/grid 分配、`height: auto`、`overflow`、`transform`、层叠上下文）× JS 动态样式的交叉点。前端位置/尺寸异常往往源于 CSS 布局覆盖了 JS 计算结果。
4. **模块契约（Contract）**：上下游类型与空值约定、入参前置条件（是否已排序/去重/校验）、错误传播边界（是否被下游 `try-catch` 吞错返回 `null` 掩盖了第一现场）。

### 🔍 判断层 A（静态扫描分流）

根据四维扫描结果，立即做出三路分流判断：

| 诊断结论 | 判定特征 | 执行动作 |
| :--- | :--- | :--- |
| **路径 1：结构性缺陷 → 转整体重构** | ① 同一份状态在 ≥3 处散落读写、无单一数据源；<br>② 模块职责严重耦合，修 A 必破 B；<br>③ 缺乏边界类型契约，到处靠散装 `if/try-catch` 兜底；<br>④ 需要在多处消费端同步打补丁才能规避问题。 | **停止单点修补！** 向用户说明结构性根因证据，转入模块化重构计划的制定（含目录结构调整与分阶段落地步骤），而不是继续在本技能内打补丁。 |
| **路径 2：确定性单点 Bug → Step 2 单次直修** | 仅涉及 1-2 个文件、无异步/竞态/缓存干扰、能完整解释从根因到故障现象的单一传播链（如明显条件反写、边界值遗漏、单处样式属性错误）。 | 进入 **Step 2** 执行唯一一次静态直修并跑验证。 |
| **路径 3：动态/复杂链路 Bug → Step 3 埋点取证** | 涉及异步时序、并发竞态、复杂状态流转、跨模块交互或静态代码无法百分百确认偏离点。 | 跳过猜测，直接生成 `session_id`（格式：`debug_YYYYMMDD-HHmmss-xxxx`）进入 **Step 3**。 |

---

## Step 2：受控单次直修（仅限路径 2）

1. 在根因源头执行最小化修复（入口强类型收窄，禁止用 `try-catch` 吞错掩盖异常）。
2. 自动运行相关测试、类型检查或复现脚本验证：
   - **验证通过** → 直接跳至 **Step 5** 完成收尾汇报。
   - **验证未通过** → **立即使用 `Edit` 还原刚才的猜测性修改**（严禁接着猜第二次！严禁使用 `git reset --hard` 破坏其他未提交改动），进入 **Step 3** 埋点取证。

---

## Step 3：注入埋点并自动复现采集证据

需注入埋点时，先阅读 `references/instrumentation-guide.md` 获取对应环境的标准模板。

### 1. 双通道落盘机制（服务端写文件 + 客户端发 HTTP）
- **服务端 / CLI / 桌面端主进程 / 测试进程（Node、Python、Go、Java、Rust、PHP、Ruby）**：
  - 直接使用**本地文件追加写入模板**，将 JSON 日志静默写入项目根目录下的 `.debug/logs/<session_id>.log`。
- **客户端 / 浏览器渲染进程（Browser JS/TS、Electron Renderer、Web UI）**：
  - 使用**本地 HTTP POST 模板**（发送至 `http://127.0.0.1:9220/debug/log?session_id=<session_id>`，请求体携带 `pwd: "<项目绝对路径>"`），由本地调试服务统一写入 `.debug/logs/<session_id>.log`。
  - 注入前先检查 `http://127.0.0.1:9220/health`；若未启动，后台运行 `node <skill目录>/scripts/debugger-server.js`（或 `launch-debugger.js`）启动服务并确认健康检查通过。

### 2. 调用链二分法选点（拒绝漫天撒网）
- 画出从“数据/事件入口”到“异常表现点”的调用链，首轮在**调用链中点及关键分叉口**注入 **≤3 处**埋点。
- 每处埋点必须回答 4 个核心问题：
  1. **入参是什么**（`input` 快照）
  2. **走了哪个分支**（`branch` 条件与布尔值）
  3. **产生了什么副作用/状态变更**（`state_change` 或 DOM `getBoundingClientRect` 实际值 vs JS 计算值）
  4. **返回值/输出是什么**（`output` 快照）

### 3. 自动触发复现与日志落盘
1. 复现前先清空当前会话日志（确保目录存在且无旧数据干扰）。
2. **全自动触发复现**：
   - 后端 / 逻辑 / 接口 Bug：直接通过单测/集成测试命令、构造最小复现脚本或 `curl` 请求触发执行；
   - 前端 / UI / 交互 Bug：优先使用 `ego-browser` 或前端测试工具自动打开页面并执行触发动作。
3. 执行后立即用 `Read` 读取 `.debug/logs/<session_id>.log`。

## Step 4：分析日志数据、第二次“重构判断门禁”与根因修复

读取 `.debug/logs/<session_id>.log` 后，按 `timestamp` 排序还原真实执行轨迹：

### 1. 二分收敛定位“首个偏离点”
- 先核对日志中的实际调用顺序是否与静态预期一致（是否多出意外调用、少掉某个回调、或异步乱序覆盖）。
- 对比各埋点的数据/样式快照：
  - **入参正常，但当前节点输出/状态开始错误** → **已锁定根因源头**！停止继续加埋点。
  - **入参在进入当前节点前就已经错误** → 在上游半区继续二分注入（每轮 ≤2 处，总轮次 ≤3 轮）。
  - **数据全程正常但 UI 仍异常** → 切换为 `visual` 埋点，对比 JS 计算尺寸与 DOM `getBoundingClientRect` / `getComputedStyle` 的差值，排查父容器 flex/grid 挤压或 CSS 默认行为覆盖。
  - **注入埋点后竞态 Bug 消失（Heisenbug）** → 说明埋点的微小耗时改变了异步交错顺序，根因锁定在附近的 `Promise / async / 事件监听` 时序缺乏串行化或取消令牌（`AbortController` / 请求序号对比）。

### 2. 🔍 判断层 B（基于运行时证据的架构判断）
拿到确凿的运行时证据后，在动手改代码前做最后一次复杂度与结构判定：

- **情形 1：日志暴露这不是简单 Bug，而是整体设计缺陷**
  - *典型证据*：日志显示多个不相关模块在同一时间窗口并发覆写同一状态、上下游契约根本不兼容、生命周期彻底倒置，单点修改只会按下葫芦浮起瓢。
  - *行动*：**立即停止直接改业务代码！** 先执行 **Step 5 的清理脚本**把所有 `#region DEBUG` 埋点和日志清理干净，随后将运行时日志证实的根因整理为架构重整依据，转入重构计划的制定。
- **情形 2：日志锁定明确的局部/单链路根因**
  - *行动*：在**首个偏离的源头节点**实施高内聚修复（修复源头 normalize/状态机/并发令牌/CSS 布局约束，绝不在下游 10 个消费处加空值判断或 `try-catch` 糊弄）。
  - *验证*：保留埋点重新跑一次自动复现，确认 `.debug/logs/<session_id>.log` 中的偏离数据已恢复正常，且回归测试与类型检查全部通过。

### 3. 盲区突破（当连续 2-3 轮埋点仍未捕获偏离时）
若多轮二分仍未找到偏离，严禁在原函数里打转：
- 对照 `references/instrumentation-guide.md` 中的**盲区自检表**，跳出已修改过的文件，检查上游数据源归一化、全局事件副作用或 CSS 层叠覆盖；
- 若用户允许使用子 Agent，也可在清理无效改动后启动一个干净上下文的独立审查子 Agent 排查盲区。

---

## Step 5：一键零残留清理与结构化汇报

无论是**修复验证通过**，还是**决定转入重构**，在结束本技能前必须执行自动清理：

1. **运行清理脚本移除所有埋点与日志**：
   ```bash
   node <skill目录>/scripts/cleanup-debug-blocks.js --session-id <session_id>
   ```
   脚本默认递归扫描当前仓库，移除所有带该 `sessionId` 的 `#region DEBUG` 代码块并删除对应日志；仅在需要限制范围时追加 `--files <文件列表>`（可先加 `--dry-run` 预览）。
2. **复跑最终测试/类型检查**：确认移除 `#region DEBUG` 代码块后项目构建与测试完全通过，且 `git diff` 中无任何残留调试代码或 `.debug/` 目录。
3. **简洁输出调试报告**：
   - **根因定位与证据**：说明哪个文件/行号发生了什么偏差（附关键运行时日志对比）；
   - **处理决策与改动**：直接修复了哪处源头逻辑，或为何判定需要转重构；
   - **验证与清理结果**：复现验证命令输出及埋点清理状态。
