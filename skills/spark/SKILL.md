# 头脑风暴与设计决策树追问（Brainstorm & Grill-Me）

> **核心信条**：后面的 `plan-review` 和 `code-review` 只能保证“把代码写对（Built Right）”，但没有任何自动化检查能挽救“从一开始就建错了方向的产品（Built from the Wrong Brief）”。本技能在动手写计划和代码前，通过**多轴线方案发散**与**设计决策树（Decision Tree）逐层追问**，把模糊想法收敛为无歧义的设计规格。

**【编码硬门禁（Hard Gate）】**：在本技能的设计方案获得用户明确拍板确认前，**严禁编写业务代码、搭建项目脚手架或直接调用编码技能**（只读探索仓库、读取文档与搜证除外；若用户在对话中明确输入 `[直接编码]` 主动要求跳过讨论除外）。

---

## Step 1：先查后问，构建“设计决策树”（Look Before You Ask）

**向用户提问代码库或已有文档里已经写明的事实，是最大的噪音。** 在发出第一条提问前，先静默完成摸底：

1. **摸底本地上下文与未知外部领域前置搜证（防无米之炊 / 防盲聊）**：
   - 检查当前仓库结构、相关模块代码、`docs/research/`（若已执行过 `research`，直接吸收其跨语言方案、成熟 SDK/CLI 引擎、社区野生技巧与踩坑结论）以及 `docs/memory/`。
   - **陌生外部领域防幻觉机制**：若 `docs/research/` 下无相关调研，但用户的想法依赖未知的外部生态、第三方平台协议或陌生技术栈：
     - **轻量事实缺口**：在给出候选路线前，先用 1～2 次 `WebSearch` 快速核实关键工具/协议的真实近况，绝不凭过时记忆或幻觉瞎编推荐方案；
     - **重度陌生领域**：主动建议用户先切入 **`research`** 做全网跨语言与社区角落摸底，再回来推演决策树。
   - **子系统拆解（防范围失控）**：如果用户的想法横跨多个彼此独立的庞大子系统（例如“做一个带多渠道解析、云端同步、会员计费和社区分享的平台”），先帮用户切出**第一期核心闭环（MVP 主干）**，按顺序逐个击破。
2. **识别协作模式（常规共创 vs 红队压力盘问）**：
   - **常规共创模式（默认）**：用户有模糊想法或面临多条路线取舍，需要多路线发散 + 决策树收敛。
   - **红队压力盘问模式（Grilling Mode）**：当用户说“盘问我”“拷问我”“挑刺”“别顺着我”“grill me”或拿出一套初步方案求检验时，跳过客套，化身严苛的首席架构师与产品负责人，专挑其**隐含假设漏洞、并发/异常死角、风控失效场景与过度设计**进行追问。
3. **画出顶层“设计决策树（Decision Tree）”主干**：
   - 将待敲定的核心问题梳理为一棵**有先后依赖关系的决策树（3～5 个顶层主干分支）**：
     - 例如：`分支 1：核心运行形态与交互入口（根决策）` → `分支 2：底层引擎复用与多渠道扩展边界` → `分支 3：并发状态流转与异常恢复策略` → `分支 4：明确不做项（Non-Goals）与设计失败红线（Anti-Goals）`。
   - **为什么必须按树遍历**：**根决策（Foundational Branch）决定了后续树枝的存亡**。先把最底层的根决策敲定，后面一大半无效分支会自动剪枝，避免无意义的发散。

## Step 2：多轴线方案碰撞 + 沿决策树逐层追问（Grill the Branches）

沿着决策树**从最底层的根分支开始，按依赖顺序逐层推演收敛**，直到消灭所有主干上的“看情况（it depends）”：

### 1. 每轮回复的《四段式视觉契约》（防回复失焦）
为了防止输出散漫的长篇大论，在每一轮讨论与追问时，终端回复必须保持以下清晰的 4 段式结构：
1. **`【1. 上下文与意图对齐】`**（首轮必含，后续按需简述）：用 2～3 句话回放从代码库/`docs/research/` 读到的关键事实，以及当前对齐的核心目标（`Goals`）、不做项（`Non-Goals`）与设计失败红线（`Anti-Goals`）。
2. **`【2. 设计决策树全局进度】`**：用状态标记列出 3～5 个顶层主干分支，让用户一眼看清当前身处哪一层、还剩哪些主干：
   - `[✓ 分支 1：已敲定 — 结论简述]`
   - `[▶ 分支 2：当前推演 — 核心问题名称]`
   - `[⏳ 分支 3：待推演 — 后续问题名称]`
3. **`【3. 当前分支多路线碰撞与追问】`**：展示当前分支的 2～3 条正交候选路线、**ASCII 架构/状态流转/交互草图**、优劣势取舍，并给出**带 `[推荐]` 标记的明确提问**。
4. **`【4. 显式默认假设清单（Stated Assumptions）】`**：列出本轮未打扰用户的次要默认决定及“若假设不成立的修改代价”（用户无需逐条回复，有异议时随时推翻）。

### 2. 真正的差异化方案碰撞（Diverge across Orthogonal Axes）
当某个核心主干分支存在多种实现路径时，**严禁拿 3 个大同小异的平庸方案或明显凑数的稻草人方案糊弄用户**。沿着真正正交的轴线给出 **2～3 个实质性候选方案**：
- **路线 A（极简务实 / 极致复用 MVP）**：最小自建代码量，最大化复用现成 SDK 或跨语言 CLI/Sidecar 引擎，最快跑通核心端到端闭环。
- **路线 B（高内聚标准架构 / 可扩展插件化）**：清晰的职责分层与策略/适配器边界，适合需要长期演进或高频扩展新渠道的场景。
- **路线 C（破局路线 / Wildcard 降维打击）**：转换问题范式或执行主体（例如结合 `research` 挖出的社区野生组合技、事件流驱动或零配置方案）。
- **可视化先行（Show, Don't Tell）**：涉及交互流程、模块协作或状态机时，必须画出精炼的 **ASCII 架构图 / 状态流转图 / 界面草图**，让用户一眼看清长什么样。

### 3. 追问与深度推演的 5 条黄金铁律（Grill-Me Rules）
1. **每次提问必须自带“Agent 推荐答案（Recommended Pick）”**：
   - 绝不向用户抛空白填空题。每个问题必须先亮出 **你的推荐路线 `[推荐]` + 核心理由 + 备选取舍**。
2. **图文同屏防遮挡规则（避免 `AskUserQuestion` 弹窗冲突）**：
   - 在终端中调用 `AskUserQuestion` 弹窗会遮挡同一轮输出的 Markdown 正文。因此，**凡是本轮回复包含多路线对比、ASCII 架构草图、决策树进度或显式默认假设清单时，一律直接在对话正文中输出编号选项（如 `A [推荐] / B / C`）**，让用户能一边看着架构图和默认假设一边自由回复或微调；仅当问题是纯独立简短选择、或将对比草图完整放入 `AskUserQuestion` 的 `preview` 字段时才可使用弹窗。
3. **按“树干 vs 树叶”划定追问深度（Decision-Changing Test）**：
   - **树干必问到底**：只要决策树上还有未敲定的**主干分叉**（会实质改变产品形态、模块边界、数据流向、外部引擎选型或核心风险的决定），必须顺着依赖树逐层问透，每次聚焦当前层级的 **1～2 个最高杠杆率主干问题**。
   - **树叶绝不追问**：一旦某个分支下探到“局部实现细节”（两边选哪个都不改变整体架构边界和外部可观察行为），立即截断该分支的追问，由你直接采用工程最佳实践记入**《显式默认假设清单》**。
4. **严禁跳过未推演分支 & 强制《自问自答深度推演（Self-Grill Protocol）》**：
   - **确认当轮 ≠ 跳过后续主干**：当用户回复“按推荐”时，仅代表采纳**当前已展开分支**的推荐方案，你必须继续推进到**下一个 `[⏳ 待推演]` 的主干分支**展开多路线碰撞，**严禁把未展开的后续分支直接略过草率出文档**。
   - **用户放权时的强制自推演**：若用户对某个分支（或剩余分支）明确表示“这块我不熟，你来定 / 剩下的你帮我拿主意”，**你绝不能省掉思考过程直接塞一个结论！** 必须执行**《自问自答深度推演（Self-Grill Protocol）》**：在回复中完整写出该分支的 2～3 条候选路线对比、潜在踩坑点、为什么排除其他路线、最终选定哪条路线的完整推导过程并展示给用户确认。**用户可以省打字，但 Agent 绝不能省掉任何一个主干分支的深度推演！**
5. **未提问的次要决定必须“显式立据”（Stated Assumptions Ledger）**：
   - 凡是替用户默认拍板的树叶级次要决定，绝不能静默脑补，必须按以下格式显式列在回复第 4 段：
     `[默认假设]：<假设内容与默认决定>（若该假设不成立的修改代价：<低/中/高及原因>）`

## Step 3：沉淀《设计规格说明书》（`docs/specs/<topic-slug>.md`）

当设计决策树的所有主干分支均已完成深度推演并敲定、无未决的架构级歧义时：

1. **按任务规模落盘**：
   - **新项目 / 新功能 / 跨模块改造（默认）**：读取并遵循 `<skill-dir>/assets/spec-template.md`，将达成共识的设计完整写入 `docs/specs/<topic-slug>.md`，涵盖：
     - **核心目标、Non-Goals 与 Anti-Goals（就算功能跑通，出现什么情况也算设计失败？）**；
     - **拍板的技术路线、决策树结论与 ASCII 架构/数据流草图**；
     - **显式默认假设清单（Stated Assumptions）**；
     - **淘汰账本（Reject Ledger：被放弃的候选方案、淘汰原因及未来什么条件下才重新启用——防止后续 Agent 走回头路）**；
     - **关键异常边界与可观察验收标准**。
   - **局部轻量特性**：若仅涉及单一模块的小型设计确认，可在对话中直接输出精简版设计结论，无需强制新建独立文件。
2. **规格自审（Spec Self-Review）**：
   - 检查生成的 `docs/specs/<topic-slug>.md`：消灭所有 `TODO / TBD / 待定`，确保架构图与边界描述一致、范围聚焦。

---

## Step 4：衔接下游工作流

向用户展示已沉淀的 `docs/specs/<topic-slug>.md` 核心结论，并根据当前状态平滑交接：
- **若碰撞过程中暴露出某个关键外部技术/协议/野生方案尚未摸底** → 引导先调用 **`research`** 对该盲区做全网跨语言深度调研，再用调研结论回填规格。
- **若设计规格已完整拍板** → 引导调用 **`create-plan`**，以 `docs/specs/<topic-slug>.md`（及 `docs/research/` 报告）为权威输入，生成包含模块化目录树、SDK 复用、接口契约与分阶段步骤的完整实施计划。
