# 创建完整实施计划

输出一份**结构清晰、自包含、丢给一个零上下文的新 Agent 也能直接按步骤编码并完成验证**的实施计划。

规划阶段仅编写或修订计划文档（沿用项目约定路径，无约定时写到 `docs/plans/<kebab-case-slug>.md`），不修改业务代码、不安装依赖、不把未执行的测试写成已通过。正文使用中文。读取 [计划模板](assets/plan-template.md) 并按任务复杂度裁剪（局部小改可合并或简化无需展开的表格，但必须保留依据，删除模板注释与占位符）。

## 1. 收集源码证据与边界

- **明确需求与边界**：从用户请求和已有决定中提取最终可消费效果、必需能力、明确不做项（不将参考产品的可选扩展擅自升级为必需交付）以及当前授权范围。
- **读取真实上下文**：读取相关源码、目录结构、调用方、`package.json`/依赖清单、锁文件、测试与脚本配置；若 `docs/specs/` 下存在已拍板的设计规格说明书或 `docs/research/` 下存在深度调研报告，优先读取并严格承接其已拍板的架构路线、淘汰账本（不重走已被否决的方案）、跨语言/SDK 选型与避坑结论。若用户仅提供练习材料或明确禁止读仓库，则严格基于给定材料规划，如实标注来源，不捏造未读文件、版本号或 API。
- **承接既有计划与审核记录**：修订已有计划时，保留原阶段命名、真实创建时间和已确认决定；已关闭的审核问题（如 R7）无新需求或新反证不重开。

## 2. 规划模块划分与文件目录树

严禁把新文件散装堆在同一目录下，也严禁把复杂页面或完整功能硬塞进单个超长文件。动手拆阶段前，必须先识别运行形态并结合工程现有约定设计清晰的模块边界与目录结构：

1. **先识别运行形态（纯前端/本地工具拒绝伪服务端冗余分层）**：
   - 若项目或功能是**纯客户端应用（SPA / 纯前端工具 / 浏览器扩展 / 无自定义后端参与的静态应用）**，严禁照搬重服务端套路去规划无意义的 `ApiService/Repository` 透传壳、SSR 水合兼容层、双份前后端 DTO 转换或无跨页共享诉求的全局 Store；直接围绕真实数据源、纯函数领域模型与视图组件组织目录。
2. **画出模块化目录结构树（含复杂前端页面拆分）**：
   - 按领域职责或功能子域划分目录（例如区分编排入口/核心领域规则、具体策略/格式实现、外部协议适配、任务/IO 基础设施、类型契约与测试），在计划开头用直观的目录树展示新增、修改、删除和关键复用文件的位置。
   - **涉及复杂前端 UI 页面或工作台时**，严禁只列一个 `Page.tsx` / `View.vue` 兜底全部请求、状态与子界面；目录树必须按职责拆出 **`页面装配壳（Page，薄路由与布局拼装） + 独立子视图组件（Components，表单/列表/抽屉/弹窗分离） + 交互与异步状态（Hooks / Store） + 纯函数转换与校验（Model / Utils）`**，使每个拟建/修改文件保持单一职责（目标单文件 ≤300 行，避免出现上千行大文件）。
3. **明确模块职责与边界**：
   - 谁是业务顺序、核心规则、状态流转和资源生命周期的**唯一权威所有者**？
   - 子模块（如具体格式编码、底层协议写入、独立子视图组件）只负责什么单一职责？
   - 旧代码中的重复逻辑、分散状态或临时清理从哪个文件退出，由谁接管？

## 3. 决策 SDK 与现成能力复用

按 **“仓库已有模块 → 语言标准库/平台内建 → 已安装依赖 → 官方或成熟第三方 SDK → 必要自建”** 的优先级决策：

- **核实能力与版本**：查看项目的依赖清单和锁文件，需要引入或查证 SDK 时优先通过 `context7` 或官方文档核对目标版本 API、运行环境、许可证与维护状态。未核实的候选标为“待查证”，绝不凭记忆编造 API 或把未验证候选写成已采用。
- **划清 SDK 与本地实现边界**：明确写出调哪个包（或内部模块）的哪个具体 API 承接通用能力（如格式编码、原子写入、任务队列），本地代码只写哪些领域规则与薄适配。**严禁一边引入或复用现成能力，一边又自己重复手写它已覆盖的解析、协议、状态管理或清理逻辑。**
- **说明取舍依据**：无需新增依赖时说明标准库或现有实现为何足够；拒绝现成 SDK 或决定自建时，必须给出真实能力缺口或约束依据。

## 4. 确定设计模式、抽象封装与接口契约

针对实际复杂度做设计，既不把职责留给编码者临场发挥，也不搞空壳透传或过度设计：

- **诊断真实变化点与模式选型**：
  - 真实存在多种算法/格式/后端变体 → 比较**策略模式**（用函数或类实现均可，统一输入输出契约，变体不接管外层主流程）。
  - 多步骤有严格先后、分支或失败回滚 → 采用**显式工作流/流水线或直接异步函数组合**（不用无顺序保证的事件监听/发布订阅承载主流程）。
  - 合法操作受状态严格约束（如排队、运行、取消、终态互斥） → 采用**显式状态机/状态转移表**或复用已有任务状态中心。
  - 隔离外部 SDK 或协议差异 → 采用**窄适配器**。
  - **克制原则**：若仅是单一稳定实现或局部规则修改，直接沿用现有函数与模块并说明理由，不为单一实现预建工厂、注册中心或只做转发的 `Service/Manager` 假封装。
- **写出五项核心设计要素**：
  1. **职责与所有权**：规则、顺序、状态、资源（如内存快照、临时文件）及**错误处理边界**分别归谁所有、谁负责释放。
  2. **对外契约与强类型约束（供新 Agent 照着写）**：给出关键入口的函数签名、强类型定义、输入输出，以及失败、取消、提交竞争（如提交后取消返回 `tooLate`）的精确语义。**用入口类型收窄（将原始输入转为已验证领域类型）和可辨识联合类型（Discriminated Union，表达预期内的失败/取消分支）替代靠抛异常走控制流；明确真正的异常在哪里原样上抛、在哪里统一捕获转换或恢复，严禁使用 `any` 或在无恢复能力的中间层乱套 `try-catch` 吞掉异常。** 拟新增符号标明“提案”。
  3. **共性、变化与选型理由**：集中什么共性、隔离什么差异，为何优于现状或备选方案。
  4. **目标调用路径与旧职责退出**：`入口 → 规则/编排所有者 → 具体策略/SDK 操作 → 结果消费` 的完整调用链，以及旧控制路径何时删除或退出。
  5. **代码落点与结构验收**：用本次一个真实的同类变更场景（如“修改统一重试/校验规则”或“新增一种格式”）说明主要改哪个入口，证明无需在多处重复修改。

## 5. 纳入性能、安全与高可用检测规划

在制定计划和验收阶段时，必须结合本次执行路径主动规划**性能检测**、**安全检测**与**高可用韧性**：

- **性能分析、按需加载与检测安排**：
  - **规模与瓶颈**：评估典型与极端输入规模（如大文件、高并发、高频调用）、内存峰值与算法/I/O 成本；不编造无依据的耗时数字（如“0ms”“50ms”）。
  - **加载时机与 CPU 执行位置**：区分启动/首屏必需能力与低频重能力（如 PDF/TIFF 编码库、大字体）。按需加载须追踪完整静态导入链（含工具栏入口、`index` barrel/re-export、顶层初始化副作用），确保重模块真正退出首屏关键路径。严格区分异步 I/O（`async/await`、动态 `import()`）与同步 CPU 计算调度（重计算阻塞主线程时需评估 Worker 或分块，并核实取消与资源释放）。
  - **性能检测方案**：在验证章节和阶段中明确用什么代表性输入、在什么环境下检查构建分包产物、首次加载轨迹、交互响应或内存释放。
- **安全边界、数据保护、高可用韧性与检测安排**：
  - **信任边界与防护控制**：梳理不可信输入（文件路径、压缩包条目、外部数据、配置）到文件写入、命令执行、渲染或网络的链路。明确路径规范化与防目录穿越/符号链接逃逸、解压大小/数量/压缩比上限、并发限额、凭证读取方式。
  - **失败恢复、原子性与高可用韧性**：涉及文件覆盖或状态迁移时，必须先在临时区处理并验证，通过原子提交（如 `writeAtomic` / `staged-write`）落盘，明确失败或中途取消时如何保留原数据、谁清理临时资源。涉及外部 I/O、异步任务或并发更新时，明确超时与幂等边界、非核心故障隔离降级、并发/状态一致性，以及携带上下文（阶段、目标 ID、原始 `cause`）的可诊断错误契约。
  - **安全与负向检测方案**：在验证计划中明确安排恶意输入、损坏数据、写入失败、超时/异常传播、提交前后取消竞争、关闭后过期结果丢弃等负向检测用例。
- **局部低风险任务**：若纯内存小数据修改确实不改变加载、I/O 或安全边界，用一两句话说明具体依据（如“仅处理内存数组排序，无外部输入、I/O 及新依赖”），不填冗长空表，但不能只写“无风险”三个字。

## 6. 编写让新 Agent 可独立执行的阶段

- **前置查证阶段（`S0`）**：当候选 SDK API、许可证、Worker 终止或底层取消/释放能力尚未核实时，先排 `S0` 隔离探针查证，写明查证方法、完成判据和**查证失败的备选或停止方案**；依赖该结论的 `S1` 保持阻塞，不将 `S0` 可开展等同于 `S1` 已就绪。
- **自包含的实施阶段（`S1`, `S2`...）**：每个阶段以动词开头且不重名，写清**前置条件、涉及文件与符号、具体实施步骤（精确到改哪个函数、怎么迁移调用方、删掉哪段旧逻辑）、开发交付物、验证命令与责任人、可观察完成判据、结束时可运行状态**。测试代码编写与测试实际运行分开表述。
- **实施就绪与授权分离**：在风险与就绪章节分别说明“技术上具备实施条件的阶段”“尚待查证阻塞的阶段”以及“当前用户已批准的范围”。

## 7. 交付前快速自检

落盘后对照以下 5 点做最后核查，有缺口直接修正后再回复用户：

1. **目录与模块**：开头是否有清晰的模块化目录树和变更总表？是否消除了同目录散装堆文件、纯前端伪服务端空壳分层，以及把复杂 UI 页面全塞进单个巨型文件的倾向？
2. **SDK 与封装**：SDK 复用表是否写清了版本状态、调用模块与自建边界？五项设计要素（职责、契约、模式选型、调用路径与旧逻辑退出、结构验收）是否完整且无假封装？
3. **性能与安全检测**：是否包含了与任务规模匹配的性能检测（含静态导入链/加载轨迹/Worker 释放）与安全负向检测（含路径边界、资源限额、失败保留原数据）？
4. **新 Agent 可执行性**：一个没看过前面对话的 Agent 仅凭这份文档，能否清楚知道每个阶段改哪个文件、写什么接口、跑哪条源自项目配置的命令验收？
5. **事实与状态准确**：未读文件、未验证 API、未运行测试是否如实标注？修订计划是否完整保留了原阶段名、已有授权与已关闭审核记录？
