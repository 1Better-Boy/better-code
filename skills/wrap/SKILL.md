# 计划完成与工程收尾（归档计划 + 提交 Commit + 合并清理 Worktree）

在编码实施与 `code-review` 终检通过后，把代码变更、计划生命周期和 Git 工作树干净地收拢闭环，确保主工作区状态整洁、历史计划可追溯且只读不可篡改。

## 1. 前置门槛核对（未过检不封版）

1. **确认验证与终检状态**：核对当前任务的最小相关测试、类型检查及 `code-review` 是否已通过，或阻塞项是否已全部清零。若存在未修复的测试失败或 P0/P1 代码缺陷，立即停止收尾并先修复问题。
2. **定位关联资源**：识别本次任务对应的**计划文档路径**（如 `docs/plans/<slug>.md`）、**当前所在工作区类型**（普通工作区或独立 Git `worktree`）以及**目标合并分支**（如主工作区当前所在的开发分支）。

## 2. 归档已完成计划（归档后只读锁定）

若本次任务存在计划文档（如 `docs/plans/<slug>.md`），在提交代码前先完成计划归档：

1. **标记最终完成状态**：在原计划文档顶部更新状态为 `已完成并归档（只读，不可编辑）`，补充实际完成日期，并将各实施阶段（如 `S0`、`S1`、`S2`）状态更新为 `已完成`。
2. **迁入归档目录**：
   - 将计划文档移动至归档目录（沿用工程约定路径；无约定时移入 `docs/plans/archive/<YYYY-MM-DD>-<slug>.md` 或 `docs/plans/archive/<slug>.md`）。
   - 若存在主计划索引（如 `PLANS.md`），将其状态同步更新为“已归档”并更新指向归档目录的相对链接。
3. **只读保护铁律**：计划一旦迁入归档目录（`docs/plans/archive/`），即成为**历史只读档案，严禁任何后续任务直接编辑或覆盖**。后续若对同一模块有新需求或变更，必须新建计划文档，必要时通过相对链接引用历史归档计划。

## 3. 安全审查与提交 Git Commit

在当前有效工作区（若使用了 `worktree`，则在 `worktree` 内）将代码变更与计划归档一并或分步提交：

1. **清理临时调试与生成噪音**：确认无残留调试块（如 `#region DEBUG`）、临时探针脚本、未使用的导入或无关格式化改动。
2. **严格检查 Diff 与凭证安全**：
   - 运行 `git status --short` 与 `git diff` / `git diff --cached` 逐项核对拟提交文件。
   - **安全红线**：确认不包含任何硬编码 API Key、Token、私钥、密码、连接字符串、`.env` 本地凭证或机器专用绝对路径。
3. **语义化提交（Commit）**：
   - 仅暂存（`git add`）本次任务相关的源码、测试与归档计划移动变更（避免盲目使用 `git add .` 把无关未跟踪文件卷入）。
   - 使用简洁、语义清晰的 Commit Message（如 `feat(<scope>): ...` / `fix(<scope>): ...`）创建新提交；**严禁使用 `--no-verify` 绕过 Git hooks**。

## 4. 合并与清理 Worktree（当使用 `worktree` 模式时）

若本次任务在独立 Git `worktree` 中执行（如通过 `/better-code worktree` 创建），完成内部 commit 后执行合并与清理（若在默认单工作区开发则跳过本步）：

1. **检查主工作区状态**：切回主工作目录（或通过 `git -C <main-worktree>` 检查），确认目标分支工作区干净，无未提交冲突变更。
2. **合并 `worktree` 分支**：
   - 在目标分支上将 `worktree` 分支合并进来（如 `git merge --no-ff <worktree-branch>` 或按项目约定的 fast-forward 策略）。
   - 若出现合并冲突，清晰列出冲突文件与原因，解决并运行最小验证检查；**未经用户明确批准，严禁执行 `git reset --hard`、重写历史或强行覆盖目标分支未提交代码**。
3. **卸载并清理临时 Worktree**：
   - 合并成功且验证通过后，若宿主环境提供 `ExitWorktree` 工具则优先调用；否则执行 `git worktree remove <worktree-path>` 移除临时工作树目录，并按需删除已合并的临时本地分支（`git branch -d <worktree-branch>`）。
   - **严禁未经用户明确要求擅自 `git push` 到远程 `main` 或默认分支**。

## 5. 结构化收尾汇报

收尾完成后，向用户输出简洁的交付清单：

```markdown
# 任务收尾与归档确认

- **提交状态**：`<Commit Hash> <Commit Message>`（所在分支：`<branch>`）
- **计划归档**：`<原路径>` → `<归档只读路径>`（已锁定为只读档案）
- **Worktree 状态**：<未使用 / 已合并回 `<target-branch>` 并清理临时目录 `<worktree-path>`>
- **最终验证结果**：<已通过的测试/构建检查命令及结果>
```
