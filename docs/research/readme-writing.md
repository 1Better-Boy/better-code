# Markdown 与 README 写作调研

- **AS_OF**：2026-11-17
- **目标**：说明 better-code 解决什么问题，让首次访问者能判断是否适合自己，并完成第一次使用。
- **范围**：Markdown 信息组织、优秀 README 的具体写法、社区反例，以及当前 README 的改写建议。本次先保留正文，只替换已确认风格的图片及对应替代文字。
- **证据标签**：`[已证实]` 表示本次读到的官方说明或仓库原文；`[社区观点]` 表示作者经验，不能当作普遍效果证明；`[设计建议/待验证]` 表示对本项目的推导。

> **后续定位修正（2026-11-17）**：用户指出，better-code 应围绕“帮助 AI 写出更好的代码”介绍，排障与收尾属于配套能力。用户已授权重写，[当前 README](../../README.md) 已按模块职责、类型契约、复用、性能与验证展开。下文以排障和交付为主要场景的开头草案属于早期建议，已被新定位取代；“先保留正文”等描述记录的是调研当时的范围。

## 统一结论

**当前主要问题是信息顺序和表达：读者先看到工程术语、流程图和技能目录，之后才知道什么时候该用、如何安装、第一次可以做什么。** 添加图片或装饰性标题不能单独解决这个问题。

建议顺序：**一句话定位 → 三类实际问题 → 安装与一次最小使用 → 按场景选技能 → 完整工作流 → 进阶说明和限制**。

Markdown 层面优先做三件事：用标题回答读者的问题；让命令可以直接复制；将长篇解释从表格和首页移到对应文档。

## 2. 三个仓库具体好在哪里

### uv：快速知道是什么，并能开始使用

`[已证实]` 第一段直接说明它是 Python 包和项目管理器；随后给出特点、安装方式和分场景命令。项目管理、工具执行等示例让读者看到实际输入和行为。

`[设计建议/待验证]` better-code 也应先说明“Claude Code 技能插件”，然后提供一条带真实任务的调用。不能照搬 uv 的性能宣传：本项目没有与其对应的性能基准。

### superpowers：把工作过程讲成用户能理解的动作

`[已证实]` README 的 “How it works” 从开始一次编码任务说起，描述澄清需求、讨论设计、拆解计划、实施和审查的过程。用户理解流程后，再看技能名称更容易建立联系。

`[设计建议/待验证]` 借鉴“遇到什么事 → 工具做什么 → 留下什么”的叙述。不要照搬它的强制 TDD、子智能体或工作树流程；这些不是本项目的默认规则。

### ripgrep：讲清行为和限制，帮助读者判断

`[已证实]` 开头直接说明文本搜索能力和默认忽略规则，正文包含 “Why should I use ripgrep?” 与 “Why shouldn't I use ripgrep?”。它也交代平台、功能差异和性能例外。

`[设计建议/待验证]` better-code 应说明技能可以单独使用、不是每次任务都需要完整流程；它通过指令指导智能体，不能保证所有架构问题、缺陷或回归一定被发现。不要复制 ripgrep 的全部长篇基准和段落顺序。

## 3. Markdown 应怎么写

### 标题帮助读者定位，而不是叠加术语

`[已证实]` GitHub 会根据标题生成文档大纲；Google 建议保持清晰的标题层级和简短介绍。

- 一个一级标题；主要部分用二级标题，必要时再用三级标题。
- 标题尽量直接：`解决什么问题`、`安装与第一次使用`、`遇到问题时用哪个技能`。
- 不用连续加粗、分割线和 emoji 代替层级。
- Google 文档中的 `[TOC]` 面向其渲染环境；不要直接当作 GitHub 通用目录语法。

### 代码块必须能让人执行或理解

- 标注 `bash`、`json`、`text` 等语言；Claude Code 会话中的 `/plugin` 和技能命令可用 `text`，不要写成终端 shell 命令。
- 在代码块前说明运行位置、前提和预期结果。
- 首次示例应完成一个小任务，不要要求读者先执行完整九技能链路。
- 示例输出如未实测，标明“预期结构”，不能伪装成本次实际运行结果。

### 表格只承载适合横向比较的信息

`[已证实]` Google 明确提醒避免包含长篇文字的表格。

当前技能表每格有多层强调、多个 `<br>` 和较长描述，窄屏阅读和源文件维护都较吃力。建议缩为“遇到的情况 / 使用哪个技能 / 会得到什么”三列，每格一句短语；详细规则链接到技能文件。

不要机械套用英文文档的固定字符数换行要求到中文；优先保证段落短、源文件好维护、实际页面好读。

### 图片帮助理解，关键信息仍应有文字

- 图片前后用一两句话说明它回答什么问题。
- 安装命令、技能名、关键条件在正文保留可复制文本。
- 为图片写描述内容的替代文字，避免只写“工作流图片”。
- 说明图不能当作真实运行截图；没有测量就不要添加“提升多少倍”“节省多少时间”。
- 仓库内文档和图片使用相对链接，适应本地阅读和不同分支。

## 4. 当前 README 的具体问题与改写方向

| 当前情况 | 对首次读者的影响 | 建议 |
| --- | --- | --- |
| 开头是“全生命周期高内聚工程引擎”等术语 | 很难立刻判断是什么、给谁用 | 先写 Claude Code 插件及三个使用场景 |
| 问题列表较长，包含“彻底终结”等绝对表述 | 缺少能核对的行为和范围 | 收敛为三类问题，分别连接对应机制 |
| 九个技能和复杂流程在安装之前展开 | 新用户要理解整套概念才能开始 | 先完成一个独立任务，再介绍全流程 |
| 功能说明与技能内部规则混排 | 首页过重，重要信息不突出 | 概览留首页，细节链接到技能文件 |
| 文案侧重“具备什么能力” | 看不出实际调用和产物 | 增加任务输入与预期输出说明 |
| “零残留”等表述像无条件保证 | 超出提示词约束能够保证的范围 | 改成要求、流程和可观察的验证步骤 |

另外，排障说明目前写“7 大语言/运行环境”，后面列出 Node.js/TS、浏览器、Python、Go、Java、Rust、PHP、Ruby 共八类。后续改写应统一计数或去掉容易失真的数量；本次未顺带更改正文。

### 建议的开头草案

以下是本项目的待评审文案，不是已经写入 README 的内容：

> **better-code 是一个 Claude Code 技能插件，用于让复杂开发任务更容易规划、排查和验收。**
>
> 当 AI 写出的代码职责混杂、同一个 Bug 反复猜改，或者任务改完后缺少验证和记录时，你可以按需调用对应技能：先明确模块边界，用运行时证据定位问题，再检查变更并整理交付记录。
>
> 你可以单独使用一个技能，也可以把调研、规划、实现、审查与收尾串起来。

对应三类问题：

| 遇到的问题 | better-code 提供的做法 | 可观察的产物 |
| --- | --- | --- |
| 需求还没厘清就动手，修改逐渐失去边界 | 调研、方案拆解、计划审核和实现约束 | 调研文档、计划、明确的模块改动 |
| Bug 反复修改，缺少能验证的原因 | 必要时进入插桩、复现、日志定位和修复验证 | 运行时证据、修复结果及清理记录 |
| 写完代码就结束，遗漏检查和项目状态 | 审查实际变更，核对验证并整理交付 | 审查结论、验证记录和按需更新的项目文档 |

这些是技能约定的行为和产物，不能宣传为每次任务无条件成功的保证。

### 建议的第一次使用

保留已经验证过的两步安装说明，并在其后加入一个独立场景。例如：**在已有代码改动的仓库中，请 Claude Code 审查本次变更**。

```text
/better-code:code-review 检查当前改动中的 Bug 和回归风险，说明具体触发条件与证据。
```

预期行为：读取工作区变更并核查调用链，给出有证据的问题或未发现问题的结论。`code-review` 默认只读，不会自动修改业务代码。这与当前 [技能规则](../../skills/code-review/SKILL.md) 一致；本次没有实际执行该使用示例，不把它写成实测结果。

### 建议的 README 结构

```text
better-code
  一句话定位 + 三类实际问题
  安装与第一次使用
  遇到什么情况，用哪个技能
  完整工作流（总览图）
  Bug 排查如何进行（取证图 + 适用条件）
  使用范围与限制
  详细文档、贡献入口和许可证
```

对比图可放在问题说明后，尺寸适度。总览图和排障图放在读者已理解用途的位置，不必三张都堆在首页开头。

## 5. 反方证据与需要避免的做法

- `[社区观点]` HN 2021 讨论的提问者也以为“需要更多图片”；回复更关注解决的问题、安装步骤和确切调用。图片数量不能证明说明有效。
- `[社区观点]` HN 2023 讨论对营销式 README、动画和过多装饰有分歧。不能把某个开源项目的品牌展示方法当成所有项目的最优解。
- `[已证实]` Appsmith 作者主张先提供最广泛读者需要的信息，再逐步进入技术细节，并把长说明链接出去。这支持信息分层，不意味着照搬 SaaS 注册入口和宣传布局。
- `[设计建议/待验证]` 区分“设计图”“实际截图”“命令示例”和“测量结果”。本项目本次生成的是解释流程的设计图。
- `[设计建议/待验证]` 不以 README 行数、图片数量、徽章数量作为质量指标。应验证读者是否能说清用途并开始一次使用。
