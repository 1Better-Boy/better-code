# README 与文章配图提示词调研

- **调研日期（AS_OF）**：2026-11-16
- **目标**：查找社区与 X/Twitter 的真实公开提示词，为现有三张 README 图片提供可追溯的改进参考。
- **范围**：提示词与设计方法调研；下文三份改编提示词尚未实际生成验证。
- **本地依据**：[README](../../README.md)、[debug-fixer 技能](../../skills/debug-fixer/SKILL.md)，以及 `docs/assets/` 中三张现有图片。
- **证据约定**：`[已证实]` 表示已读到对应原文或实现，不代表审美效果有保证；`[多方印证]` 表示独立来源采用相似方法；`[社区实战/待实测]` 表示作者提供案例，但本项目尚未复现。本文的配色、字数预算与布局建议属于设计判断。

## 1. 统一调研结论

**建议先缩减信息、确定构图，再改变画风。** 现有图片的问题不只在颜色：对比图同时包含目录树、代码、状态机和日志；排障图底部又重复了一条流程。缩小后，装饰和细节会争夺注意力。这是根据本地图片作出的设计判断，并非对原始生成提示词的判断——本次没有找到原始提示词。

推荐尝试统一的浅底工程插画：米白底、深色线条、青绿主强调色、少量陶土橙标记风险。三张图共用视觉规范，分别使用流程、对比、排障三种信息结构。喜欢手绘时，只替换线条质感和图标风格，不同时更改全部布局。

- **直接参考**：宝玉的文章转信息图提示词、Abhishek 的 sketchnote 提示词。
- **借鉴结构**：`baoyu-article-illustrator` 的 Type × Style × Palette 拆分，以及 `ZONES / LABELS / COLORS / STYLE / ASPECT` 提示词组织方法。
- **本地需要补齐**：准确的技能名称、四阶段关系、排障的条件分支，以及每张图允许展示的文字清单。
- **无需引入依赖**：当前任务是参考提示词，不需要安装图像 SDK、第三方技能或改变已有插件运行方式。

## 3. 原文中值得借鉴的写法

### 3.1 宝玉：先压缩文章，再画图

**来源**：[X 原帖](https://x.com/dotey/status/1993567848564686926)；[中英文转载](https://opennana.com/awesome-prompt-gallery/prompt-546)。`[已证实：原帖内容]`

原文短摘：

> Hand-drawn illustration style, landscape orientation (16:9 aspect ratio).
>
> Keep information concise, highlighting keywords and core concepts. Utilize ample whitespace to clearly emphasize key points.

可迁移的方法：横版构图、少量图标、只保留核心概念、语言与正文一致。原帖还包含人物替代等要求，与本项目工程图无关，不纳入改编。

**对本项目的改编**：把“九个技能的所有卖点”缩成“四个阶段 + 一条全程记忆层”；详细职责交给正文表格。

### 3.2 Abhishek：把画风写成材料与颜色

**来源**：[公开线程转载](https://threadreaderapp.com/thread/2011799035599040600)；[X 原始链接](https://twitter.com/HeyAbhishekk/status/2011799035599040600)。`[社区实战/待实测]`

原文短摘：

> Use a pristine white paper background (no lines).
>
> Use colored markers (specifically teal, orange, and muted red) for simple shading and accents.

作者先把内容总结为短概念，再指定黑色细线笔、彩色记号笔和清晰手写文字。原版采用 A4、中央标题和放射布局；README 工作流适合改成横向阅读，不照搬其比例和放射结构。其“perfect”等宣传措辞不作为质量保证。

### 3.3 宝玉配图工具：结构、画风、配色分开控制

**来源**：[提示词模板](https://github.com/JimLiu/baoyu-skills/blob/main/skills/baoyu-article-illustrator/references/prompt-construction.md)；[技能入口](https://github.com/JimLiu/baoyu-skills/blob/main/skills/baoyu-article-illustrator/SKILL.md)。`[已证实：模板实现]`

模板将流程图写成 `Layout / STEPS / CONNECTIONS / STYLE / ASPECT`，将对比图写成 `LEFT SIDE / RIGHT SIDE / DIVIDER / STYLE / ASPECT`。因此“图解释什么”和“图看起来怎样”可以独立修改。

原文短摘：

> Clean composition with generous white space. Simple or no background. Main elements centered or positioned by content needs.

另一个具体提醒是：色号和颜色名称只是绘制说明，模型可能把它们画成可见标签，应明确禁止这种输出。这是模板作者记录的风险，本项目尚未复现。

**对本项目的改编**：先列节点与连接关系，最后加共用画风；允许出现的文字单独列清单。未将该外部技能的安装、工具调用或确认流程作为本次执行指令。

### 3.4 官方指南：用设计说明代替关键词堆砌

**来源**：[Google AI 指南](https://dev.to/googleai/nano-banana-pro-prompting-guide-strategies-1h9n)与 [OpenAI 指南](https://developers.openai.com/api/docs/guides/image-prompting)。`[多方印证：提示方法]`

两者都强调用途、具体构图、准确文字和逐项修改。Google 的例子区分编辑式插画、技术图解、手绘白板；OpenAI 明确要求给参考图分配角色，并在修改时说明需要保留什么。

因此可以写“用于 GitHub README，预计按 900 像素宽显示，四个等宽分区，单一阅读方向”，而不要只写“高级、科技、4K”。像素与比例还需在实际生成工具支持的参数中设置，写进提示词本身不保证输出尺寸。

## 4. 三张图的改编提示词

以下均为根据上述来源及本地内容新写的提示词，**不是原作者逐字提示词，也未验证生成效果**。完整提示词由“共用视觉规范 + 对应单图说明”组成；每次只生成一张。

### 4.1 共用视觉规范

```text
为开源开发工具的 GitHub README 制作一张横版 16:9 工程说明插画。
目标读者是开发者。图片将在约 900 像素宽的页面中显示，核心关系应在缩小后仍能看懂。

视觉规范：
米白色背景 #F7F5F0，深炭色文字与线条 #24272B。
青绿色 #287D75 表示主流程或正确路径，陶土橙 #C97C5D 仅用于风险与异常分支。
使用简洁的二维几何图形、统一线宽和低饱和色块。
留出宽阔边距与分区间距；标题、节点、辅助标签形成清晰的三个层级。
文字使用清晰的印刷体；英文技能名可以用等宽字形，中文保持简洁清楚。
色号和颜色名只用于绘制，不得作为文字显示在图片里。

信息约束：
只能使用单图说明中列出的可见文字，不添加宣传口号、数字或功能。
所有箭头必须对应明确关系，不添加装饰性的交叉连线。
不使用发光、霓虹渐变、玻璃面板、金属质感、粒子、密集背景网格或伪造代码。
优先保证可读性和关系准确；不要为了塞入内容而缩小文字。
```

这里的色号和显示宽度是本次设计建议，不是来源推荐的唯一方案。若尝试手绘版本，只将“二维几何图形、统一线宽”替换为“轻微不规则的黑色细线笔与少量平涂”，保留布局、文字和配色，便于比较。

### 4.2 工作流总览：`workflow-overview.png`

借鉴：宝玉的精简信息原则、配图工具的 Flowchart / Framework 模板。

```text
图的目标：让读者理解四阶段工作流，以及 doc-memory 贯穿全程。
这是概念总览，技能可以按任务独立使用，不把九个技能画成每次必须完整执行的九步。

布局：
顶部左侧放标题“better-code”，下一行放“从调研到交付”。
中部从左到右安排四个等宽分区，分区间仅用一根清晰箭头连接。
每个分区只包含阶段名、一个简洁线性图标，以及两个技能名称。
图标分别暗示探索、规划、构建、检查，不增加文字解释。

四个分区的可见文字：
“探索”：“research”“spark”
“规划”：“create-plan”“plan-review”
“构建”：“better-code”“debug-fixer”
“交付”：“code-review”“wrap”

底部用一条纤细的横向带贯穿四个分区。
横带只写“doc-memory · 全程记忆”，用四条短连接线关联四个阶段。
记忆横带不能被画成第五个顺序步骤。
在标题下加一行短注释“按需调用，也可串联”。

不要展示文件树、代码、终端或功能说明段落。
```

技能名是概念标签，不充当完整安装后的命令写法；精确调用方式保留在 README 的命令示例中。

### 4.3 编程方式对比：`vibe-vs-better-code.png`

借鉴：配图工具的 Comparison 模板；使用相同对齐关系降低比较成本。

```text
图的目标：比较三种工程问题与对应的改进方法。

布局：
左右两列，使用细分隔线与完全对齐的三行，左右信息量相当。
左列标题“缺少工程约束”，右列标题“better-code”。
每个格子只保留一个大图形和一条短标签。

第一行：
左边画四个没有明确边界、相互缠绕的小模块，标签“职责混杂”。
右边画三个边界清晰、接口相接的模块，标签“模块边界”。

第二行：
左边画一个只有问号和重复回转箭头的小循环，标签“猜测修补”。
右边画放大镜检查一条简化证据记录，再指向修复标记，标签“运行时证据”。

第三行：
左边画一份草稿被直接抛向终点，标签“改完就停”。
右边画检查清单与归档盒，标签“验证与归档”。

使用共用视觉规范。左列只用少量陶土橙，右列只用少量青绿。
除上述两列标题及六条标签，不出现其他文字。
不绘制真实代码、目录树、日志行、状态机或虚构的效率百分比。
不将左边夸张成灾难画面，依靠对应关系说明差别。
```

### 4.4 实证排障：`debug-fixer-engine.png`

借鉴：Flowchart 模板与官方的明确连接关系原则；依据本地 debug-fixer 技能核对分支含义。

```text
图的目标：解释进入运行时取证后的排障主路径，以及发现结构问题时转入规划的分支。
这不是完整算法手册；不展示所有实现细节。

标题：“debug-fixer”
副标题：“运行时取证路径”

布局：
中部六个简洁节点从左向右排列，依次用单向实线箭头连接：
“扫描” → “取证” → “定位” → “修复” → “验证” → “清理”。
最后三个节点严格顺序连接，不能画成修复与清理并行。

“取证”节点下方安排一个紧凑的辅助区域：
“后端”与“浏览器”两条细线分别指向同一个文档图标；
文档图标只标记“日志”，再连接回“定位”节点。
该辅助区域不增加独立的第二条完整流程。

顶部放一个小的陶土橙色分支框，写“结构问题”。
从“扫描”和“定位”分别引一条条件分支线到这个框。
框后依次连接“清理埋点”与“create-plan”，明确先清理再进入规划。
“结构问题”分支从主路径分出，不能被画成主路径每次都经过的必选步骤。

不展示端口、完整日志路径、JSON、代码或大段解释。
不在底部重复绘制流程。仅使用列出的标题、标签与副标题。
```

说明：本地技能还允许一次高把握的静态直修，并要求失败后转入取证；本图标题明确限定为“运行时取证路径”，不把概念图当成完整执行规范。完整要求仍以技能正文为准。

## 5. 真实坑点与证据边界

| 坑点 | 依据 | 应对 |
| --- | --- | --- |
| 把“提示词库”中的重建文本当原作者原话 | `[已证实]` [ZeroLu 的 README](https://github.com/ZeroLu/awesome-gpt-image/blob/main/README.md) 明确标出部分 `reconstructed` 条目；文章黑板案例只有宣传句 | 每条注明原文、转载或改编；不把效果展示文案当可复用完整 prompt |

| 颜色说明被画成文字 | `[社区实战/待实测]` [提示词构造模板](https://github.com/JimLiu/baoyu-skills/blob/main/skills/baoyu-article-illustrator/references/prompt-construction.md)专门提醒 | 明确禁止显示色号、色板名称和设计指令 |

## 6. 待验证项与下一步

1. 先用工作流总览做一张候选图，检查浅底、少色和简化信息是否符合期望，再扩展到另外两张。
2. 在实际生成工具中设置支持的横向尺寸；以 900 像素及约 390 像素宽预览。若手机宽度看不清，不继续缩小字号，应拆分图片或把细节移回正文。
3. 核对九个技能名、四阶段顺序、doc-memory 的全程关系；排障图重点核对条件分支以及验证与清理的顺序。
4. 对比几何线条与轻微手绘两个版本时保持文字、布局和配色一致，以便判断画风本身的效果。
5. 保存最终提示词、生成工具、尺寸及选中的图片，方便后续复现和修订。是否替换 README 配图属于后续实施，本报告没有执行图片生成或替换。
